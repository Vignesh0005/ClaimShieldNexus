# Throughput benchmark

Generated by `scripts/benchmark_throughput.py` on 2026-10-08 13:58 UTC. These are measurements from one run on one machine, not targets.

## Setup

| | |
|---|---|
| Database | sqlite (throwaway file) |
| Processing | one claim at a time, one process, detection in-process |
| ML model | local artifacts v1.0.0 |
| Claims | 500 synthetic claims in date order, 146 with planted patterns |
| Machine | Windows 11, AMD64, 8 logical CPUs, Python 3.12.6 |

## Results

|---|---|

| Throughput | 5.41 claims/second (325 claims/minute) |
| Latency per claim, end to end (validate, store, detect, commit) | p50 145 ms, p95 442 ms, p99 655 ms, mean 185 ms |
| Latency per claim, detection pipeline only | p50 102 ms, p95 325 ms, p99 503 ms, mean 131 ms |
| Claims with at least one finding | 213 of 500 |
| Claims routed to a case | 173 of 500 |

## How to read this

- Latency grows through the run because each claim is compared with its provider's and member's earlier claims, and busy flagged providers accumulate history. The p95 and p99 figures are mostly those providers.
- This is a single worker. 325 claims/minute is **below** 1,000 claims/minute.
- Parallel workers, PostgreSQL and Redis have not been measured. See `docs/scaling.md` for what would need to change and what is still unknown.
